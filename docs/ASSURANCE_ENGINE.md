# RCHAIN-COMPLIER Assurance Engine

A Node.js engine for task-bound, signed evidence, durable recovery and independent deterministic verification. RChain is an integration workload, not the product protocol. This package preserves the repository's event, compiler and SQLite architecture.

Requires **Node.js 22.18 or later** on Linux. No runtime npm dependencies. Install the release tarball with `npm install ./aixaria-assurance-engine-0.3.0.tgz`. Use is subject to the included proprietary LICENSE; this release does not grant new redistribution rights.

## Quick start

From the repository:

```sh
npm ci
npm run demo
npm run pack:assurance
npm run verify:assurance-package
```

The demo creates three real Node processes with separate Ed25519 identities, persists signed task/evidence/receipts, verifies a correct claim, restarts from WAL journals without duplicating work, rejects modified bytes and signatures, and independently refutes a false claim. Outputs are retained under `artifacts/assurance-demo`; choose a fresh directory for another demo: `npm run assurance -- demo /tmp/my-demo`. Existing demo history is never erased automatically.

In a separate consuming project:

```sh
npm install ./aixaria-assurance-engine-0.3.0.tgz
npx assurance demo ./demo
npx assurance verify ./demo/sample.evidence.ndjson ./demo/sample.trust.json
```

`sample.trust.json` is a convenient set of review pins generated by the producer. For independent review, retain/confirm its policy, task, claim and package digest through a separately trusted channel. Downloading evidence and pins from the same untrusted source does not establish identity or provenance.

## Public interface

```js
import { initializeEngine, AssuranceEngine, verifyEvidence } from "@aixaria/assurance-engine";

initializeEngine("./engine"); // empty private directory; never overwrites identities
const engine = await AssuranceEngine.open("./engine");
try {
  const result = await engine.run({
    schema: "assurance-workload/v1",
    domain: "arithmetic",
    operation: "integer-sum/v1",
    predicate: "integer-sum",
    input: { schema: "integer-sum-input/v1", values: [2, 3, 5] },
    value: 10,
  });
  const report = verifyEvidence(result.evidence, result.context);
  console.log(report.status); // PASS
  await engine.recover(); // restart/rejoin all three identities from existing journals
} finally {
  await engine.close(); // idempotent
}
```

The workload asserts a bounded result about JSON input. It does not authorize shell commands or external mutations. `run` returns `{evidence, context, report}`; report status is computed, never trusted from a stored assertion. Each report identifies the selected operation and includes explicit process-independence and external-provenance limitations. Identical workloads in one workspace reuse the original submission and receipts. The workload ID hashes the complete canonical workload including its asserted value; changing the assertion creates a new task. Imported legacy TaskEnvelopes keep their existing IDs and are checked against reviewer pins.

The supported root exports are `initializeEngine`, `AssuranceEngine`, `createSubmission`, `validateWorkload`, `workloadId`, `exportEvidence`, `parseEvidence`, `packageDigest`, `verifyEvidence`, `AssuranceError`, protocol helpers and types. `/lattice` exposes existing low-level signing, journal, replay and `startNode` APIs. `/integrations/rchain` exposes `RCHAIN_VERIFIERS`. TypeScript declarations are shipped.

## CLI and operation

| Command | Result |
| --- | --- |
| `assurance init DIR [core\|rchain] [MODULE]` | Create private identities and versioned membership/configuration |
| `assurance run DIR WORKLOAD.json PREFIX` | Run three processes, write `PREFIX.evidence.ndjson`, `.trust.json`, `.report.json`, then stop |
| `assurance verify PACKAGE TRUST [DIR]` | Offline signature, binding and local replay verification; optional operator workspace selects trusted integrations |
| `assurance status DIR` | Journal counts, capacity, roots, missing dependencies, blocks and equivocations |
| `assurance serve DIR` | Keep the three loopback event services alive; SIGINT/SIGTERM stops them |
| `assurance demo [DIR]` | Verified positive lifecycle, restart, negative claim and deterministic tamper |

Stdout is machine-readable JSON; diagnostics use schema `assurance-diagnostic/v1` on stderr. Task diagnostics include task ID, status, events, independent verifier count and duration. `processIds` and `endpoints` support local monitoring. Health and bounded signed event exchange remain available through the existing loopback service (`GET /health`, `/metrics`, `/identity`, `/events`, `/view`; `POST /events`, `/sync`). There is no remote signing or arbitrary execution API. `serve` reserves the workspace; submit signed events through the low-level API or use the SDK in the same supervisor. A second `run` supervisor receives BUSY.

CLI exits: **0** success/PASS, **1** FAIL, **2** BLOCKED, **3** operational or invalid invocation. Engine startup, execution and recovery failures use `AssuranceError` codes with retained native causes; low-level legacy APIs can still throw their existing errors. Missing files/SQLite/transport failures can carry native causes. Inspect `code`, not human prose. Error codes include INVALID_INPUT, RESOURCE_LIMIT, INTEGRITY_MISMATCH, BINDING_MISMATCH, INCOMPLETE_EVIDENCE, UNSUPPORTED_VERIFIER, QUORUM_MISSING, CONFLICT, CLAIM_REFUTED, VERIFIED, BUSY, TIMEOUT and IO_ERROR.

One workspace admits one supervisor through a separate SQLite exclusive transaction. The OS releases the lock on process death; children stop when their supervisor's IPC connection disappears. No PID guessing or stale-lock deletion is required. Do not also run independent signing processes against these identities. `recover()` and close/reopen retain keys and journals. Export and independently retain evidence before moving a workspace; never copy a live SQLite file without its WAL or a proper SQLite backup.

## Status semantics

| Status | Meaning |
| --- | --- |
| PASS | Policy/task/claim pins match, signatures and relevant causal provenance validate, registered deterministic replay matches receipts, and two distinct identities other than task/claim submitters reproduce support |
| FAIL | Malformed/tampered package, reviewer binding mismatch, or two independent conclusive refutations of the targeted claim |
| BLOCKED | Missing dependencies, unsupported verifier, incomplete quorum, quarantined/unreproduced relevant evidence, or contradictory reproduced results |

The reviewer evaluates the target claim's causal cone and attached evidence. Unrelated retained unresolved tasks do not invalidate a valid target, but remain visible in full replay and diagnostics. Any reproduced counterexample to the target prevents PASS; a single refutation remains BLOCKED pending the second identity. Multiple identities on one host are process independence, not independent organizations or a defense against a malicious host operator.

## Evidence wire format and trust

`assurance-evidence-package/v1` is canonical UTF-8 NDJSON: a bounded manifest followed by ascending, unique event IDs, one canonically serialized signed event per line, LF terminated. The manifest contains the policy, policy digest, task envelope ID, task event ID, claim ID, event root and count. Every signed event is admitted with the original Ed25519 domain separation and SHA-256 rules. Existing restricted canonical JSON permits safe integers, scalar Unicode, sorted ASCII keys and bounded plain data; it rejects duplicate keys, floats, accessors, cycles and ambiguous encodings. It is not RFC 8785.

`packageDigest` is SHA-256 of `assurance-evidence-package/v1\0` plus the exact package bytes. The event root preserves the existing policy-bound event-set hash. The package is authenticated through its signed events; there is no fabricated aggregate signature. A reviewer must supply `expectedPolicyDigest`, `expectedTaskId` and `expectedClaimId`. Pin `expectedPackageDigest` as well to detect export truncation/replacement even if someone repairs counts/root. A coherent subset without a retained package digest cannot establish that other network evidence was never withheld. Replay cannot prove network completeness or an upstream execution that the verifier does not perform.

Schemas document structure; runtime admission additionally checks canonical bytes, signatures, identity policy, content hashes and semantic task binding. JSON Schema alone cannot verify a package.

## Integration boundary

`core` registers only `integer-sum/v1`. `rchain` additionally enables the existing pinned C192 witness adapter. Existing lattice examples retain their legacy default registry so RChain workloads continue to operate. The C192 adapter validates the exact witness declaration and locally reproduces its bounded interpretation. It does not reexecute upstream Cargo, verify arbitrary run URLs/output bytes or prove devnet finality. Use the retained upstream workflows and raw artifacts for those claims.

Another integration can export a **trusted local** ESM module:

```js
export const VERIFIERS = new Map([
  ["my-operation/v1", (claim, evidence) => {
    // Check schema, input bounds, claim scope and evidence IDs/digests here.
    // Return deterministic {verdict: SUPPORTED|REFUTED|INCONCLUSIVE, artifact: bounded JSON}.
  }],
]);
```

Pass its absolute/local file path at initialization; all three processes and the independent reviewer use the registered implementation. `assurance verify PACKAGE TRUST OPERATOR_DIR` loads that explicitly selected registry. The module's entry-file digest is pinned in workspace configuration; drift blocks restart. Review its dependencies too: the entry digest does not attest a dependency closure, environment or external service. Plugins run with operator privileges and must be trusted, deterministic and bounded. No module path, URL or executable is accepted from workload/evidence data. For hostile third-party code, build a separate sandbox integration; this release supplies no code sandbox.

## Limits and release boundary

Defaults: one active task and zero waiting tasks; BUSY backpressure; three processes; 4096 events per journal; 32 events per atomic batch/page; 16 KiB per record/workload; 8 MiB per package; at most 15 verifier operations; 32 HTTP connections and 16 in-flight requests per node (HTTP 429 on saturation), 64 requests per socket; 3-second peer requests within a 10-second sync deadline; 15-second task deadline (SDK configurable 100–60000 ms); 10-second startup and 2-second graceful shutdown before SIGKILL. SQLite uses WAL, FULL synchronization and 250 ms writer busy timeout.

The product is intentionally bounded local infrastructure. There is no automatic compaction, distributed service authentication, dynamic membership, key rotation, remote plugin execution or universal executor. At capacity, retain the canonical package and explicitly start a new workspace; do not erase evidence to make a test pass. Process-kill recovery is executable evidence, not a claim about every power-loss/storage-controller failure. Full-set replay currently scans bounded history and has no validated maximum-throughput SLA. No maximum code-quality or efficiency score is claimed.

Compatibility and migration rules are in VERSIONING.md in the tarball and `docs/ASSURANCE_VERSIONING.md` in the repository. SECURITY.md describes trust boundaries and reporting. The existing dashboard, compiler APIs, research workflows and historical evidence remain in the source repository; the distributable contains only the Node assurance dependency graph, schemas, declarations and product/security/license documentation.
